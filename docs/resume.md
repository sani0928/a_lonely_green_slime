# 이력서 반영 초안 - A lonely green slime

이 문서는 `A lonely green slime` 프로젝트를 이력서에 반영할 때 사용할 수 있는 핵심 소개 문구와, 회사 입장에서 매력적으로 보일 수 있는 기술 포인트를 정리한 초안이다.

## 1. 프로젝트 한 줄 소개

- Phaser 기반의 2D 생존형 웹게임을 직접 설계·구현하고, Django REST API를 붙여 리더보드·피드백·플레이로그까지 운영 가능한 형태로 만든 개인 프로젝트

## 2. 이력서용 짧은 소개 문구

### 버전 A. 범용/안전형

- `A lonely green slime`은 Phaser 기반 웹 액션 게임으로, 프론트엔드 게임 로직뿐 아니라 Django 백엔드 API를 함께 구축해 리더보드, 익명 플레이로그 수집, 사용자 피드백 저장까지 포함한 풀스택 개인 프로젝트입니다.

### 버전 B. 기술 강조형

- 실시간 게임 플레이 경험과 운영 데이터를 함께 설계한 프로젝트입니다. Phaser로 전투/성장/난이도 시스템을 모듈화했고, Django REST API로 리더보드와 플레이로그 수집 기능을 구축해 밸런스 개선에 활용할 수 있는 구조를 만들었습니다.

### 버전 C. 회사 관점 어필형

- 단순히 게임을 구현하는 데서 끝내지 않고, 사용자 기록 저장, 익명 로그 수집, 주기별 리더보드 집계, 피드백 접수 기능까지 연결해 “출시 후 운영과 개선”까지 고려한 형태로 개발했습니다.

## 3. 이력서 bullet 초안

### bullet 1. 전체 구조

- Phaser + JavaScript 기반으로 게임 클라이언트를 구현하고, Django REST API로 점수 기록·피드백·플레이로그를 처리하는 풀스택 구조를 설계했습니다.

### bullet 2. 시스템 설계

- 플레이어, 적, 보스, 충돌, 난이도, 업그레이드, 뱃지, HUD 등을 시스템 단위로 분리해 게임 로직을 모듈화했고, 기능 추가와 밸런스 조정이 가능하도록 구조를 정리했습니다.

### bullet 3. 데이터 기반 개선

- 회원가입 없이도 사용할 수 있는 익명 ID/런 ID 체계를 설계하고, 플레이 시간·피격 원인·킬 수·분 단위 스냅샷·장착 뱃지 정보를 저장해 실제 플레이 데이터를 바탕으로 난이도와 보상 구조를 개선할 수 있게 했습니다.

### bullet 4. 사용자 경험

- 다국어(i18n), 설정 저장, 일시정지/오토 일시정지, 단계별 BGM 전환, 게임오버/클리어 오버레이 등 사용자가 반복 플레이하기 쉬운 UX를 직접 구현했습니다.

### bullet 5. 운영 기능

- 전체 최고 점수뿐 아니라 기간별(`7d`, `30d`, `1y`) 리더보드를 제공하고, 동일 닉네임의 최고 기록만 반영하도록 집계 로직을 분리해 운영 관점의 데이터 노이즈를 줄였습니다.

## 4. 회사 입장에서 매력적으로 보일 포인트

### 4.1 단순 구현보다 "운영 가능한 서비스"에 가깝다

- 프론트엔드 화면만 만든 프로젝트가 아니라, 기록 저장 API, 피드백 수집, 플레이로그 적재, 기간별 집계가 함께 있다.
- 회사 입장에서는 "만드는 사람"보다는 "만들고 나서 개선까지 생각하는 사람"으로 보이기 쉽다.

### 4.2 데이터 수집 목적이 명확하다

- 플레이로그가 단순 이벤트 적재가 아니라 난이도 조정과 밸런싱을 위해 설계되어 있다.
- `contact_hits`, `projectile_hits`, `shooter_*`, `snapshots`처럼 실제 개선 액션으로 연결될 필드가 분명하다.

### 4.3 구조화 능력을 보여주기 좋다

- `GameScene` 하나에 기능을 몰아넣지 않고 `playerSystem`, `enemySystem`, `difficultySystem`, `badgeSystem`, `bossSystem`, `hudSystem` 등으로 나눈 점이 좋다.
- 이 구조는 기능 확장과 유지보수를 고려했다는 신호로 읽힌다.

### 4.4 사용자 경험과 기술 구현의 균형이 있다

- 다국어, 저장 설정, 기간별 리더보드, 자동 닉네임 처리, 유효성 검증처럼 자잘하지만 실제 서비스에서 중요한 요소가 구현돼 있다.
- "기능은 돌아가는데 서비스 품질은 낮은 프로젝트"와 구분되는 지점이다.

### 4.5 게임 프로젝트이지만 일반 웹 서비스 역량으로 번역 가능하다

- 상태 관리
- API 연동
- 데이터 검증
- 로그 수집
- 사용자 행동 기반 개선
- 도메인 로직 분리

위 요소는 게임 회사뿐 아니라 일반 웹 서비스 회사에도 충분히 전달 가능한 역량이다.

## 5. 직무별로 강조하면 좋은 포인트

### 프론트엔드 지원 시

- Phaser 기반 실시간 게임 루프와 HUD/UI를 구현한 점
- 로컬 스토리지 기반 설정/언어 저장
- 다국어 리소스 분리와 UI 반영
- 시스템 단위 모듈화로 복잡한 상태를 관리한 점

### 백엔드 지원 시

- Django REST API 설계
- 닉네임 검증, 자동 닉네임 발급, 점수 갱신 정책
- 기간별 리더보드 집계
- `update_or_create`, 유니크 제약, 인덱스 설계
- 플레이로그 sanitize 및 JSON 스냅샷 저장

### 풀스택 지원 시

- 게임 클라이언트와 운영 API를 함께 설계한 점
- 프론트 수집 데이터가 백엔드 저장 구조와 바로 연결되도록 맞춘 점
- 기능 구현, 운영 로그, 개선 포인트까지 하나의 사이클로 묶은 점

### 게임 클라이언트/게임플레이 지원 시

- 전투, 성장, 난이도 상승, 보스, 뱃지 빌드, Endless 구간까지 포함한 코어 루프 설계
- 시간 경과와 플레이어 성장도를 함께 반영한 난이도 조절 로직
- 밸런싱을 감으로만 하지 않고 플레이로그 기반으로 개선할 수 있게 한 점

## 6. 면접에서 설명하기 좋은 기술 포인트

### 포인트 1. 왜 플레이로그를 넣었는가

- "게임은 만들고 끝나는 게 아니라, 사용자가 어디서 이탈하는지 알아야 개선할 수 있다고 생각해 익명 플레이로그를 수집했습니다."

### 포인트 2. 왜 시스템을 쪼갰는가

- "게임 기능이 늘수록 한 파일에 로직이 몰리면 밸런스 조정과 기능 추가가 어려워져서, 전투/난이도/UI/업그레이드/보스 로직을 분리했습니다."

### 포인트 3. 왜 기간별 리더보드를 만들었는가

- "전체 랭킹만 있으면 신규 유저가 진입하기 어려울 수 있어 최근 7일·30일·1년 기준으로도 기록을 볼 수 있게 했습니다."

### 포인트 4. 무엇을 개선할 수 있는 구조인가

- "현재 구조에서는 특정 시간대 이탈률, 원거리 적 피격 비중, 특정 뱃지 조합의 성능 편차 등을 확인해 패치 방향을 결정할 수 있습니다."

## 7. 최종 추천 문안

이력서에는 아래 정도 길이가 가장 무난하다.

- Phaser 기반 2D 웹게임과 Django REST API를 함께 구현한 풀스택 개인 프로젝트입니다. 전투/성장/난이도/보스 시스템을 모듈화했고, 기간별 리더보드와 익명 플레이로그 수집 기능을 구축해 실제 사용자 데이터를 바탕으로 밸런스를 개선할 수 있는 구조를 설계했습니다.

## 8. 과장 없이 말해야 하는 부분

- 현재 확인 가능한 코드 기준으로 강하게 말해도 되는 것은 "구현", "설계", "수집 구조", "리더보드/로그/피드백 구축"까지다.
- 실제 트래픽 규모, 사용자 수, 성능 수치, 운영 지표 개선 효과는 확인되지 않았으므로 이력서에 수치 성과처럼 쓰지 않는 편이 안전하다.
- 배포 경험을 강조하고 싶다면 실제로 본인이 배포/운영한 범위를 본인 확인 후 별도로 문구화하는 것이 좋다.

## 9. 사용자 이력서 양식에 맞춘 최종 문안

### 버전 1. 게임플레이/성능 중심

- A lonely green slime (1인 개발, 사용 기술스택 : JavaScript, Phaser, Django REST Framework)
A lonely green slime은 Phaser 기반으로 개발한 2D 생존형 웹게임으로, Django REST API를 연동해 리더보드, 피드백, 플레이로그 수집 기능까지 함께 구축한 풀스택 개인 프로젝트입니다.
개발을 진행하며 적 수가 많아지는 후반부와 Endless 구간에서 몬스터 이동 및 충돌 처리 비용이 커질 수 있는 구조적 문제가 있었습니다.
이를 해결하기 위해 적 탐색 로직에 spatial hash grid를 적용해 적 분리와 타겟 탐색에 재사용하도록 구조를 개선했고, 시스템 로직도 전투, 난이도, 보스, HUD 단위로 모듈화했습니다.
또한 회원가입 없이도 플레이 데이터를 수집할 수 있도록 익명 ID와 run ID 기반 플레이로그를 설계해 피격 원인, 킬 수, 분 단위 성장 스냅샷을 저장하도록 구현했습니다.
그 결과 후반부에도 많은 적을 안정적으로 처리할 수 있는 구조를 만들었고, 감각에만 의존하지 않고 실제 플레이 데이터를 기반으로 난이도와 보상 밸런스를 개선할 수 있게 했습니다.

### 버전 2. 운영/데이터 수집 중심

- A lonely green slime (1인 개발, 사용 기술스택 : JavaScript, Phaser, Django REST Framework)
A lonely green slime은 Phaser 기반의 웹 액션 게임으로, 단순 플레이 구현에 그치지 않고 Django REST API를 활용해 기록 저장과 운영 기능까지 함께 개발한 프로젝트입니다.
초기에는 밸런스 조정이 플레이 감각에 의존할 가능성이 높고, 전체 리더보드만으로는 신규 유저 경험과 최근 플레이 흐름을 파악하기 어렵다는 문제가 있었습니다.
이를 해결하기 위해 기간별 리더보드(`7d`, `30d`, `1y`)를 분리하고, 동일 닉네임은 최고 기록만 반영하도록 집계 로직을 설계했습니다.
또한 익명 플레이로그 수집 기능을 구현해 플레이 시간, 피격 유형, 최종 점수, 분 단위 스냅샷, 장착 뱃지 정보를 저장하도록 구성했습니다.
그 결과 사용자 기록을 운영 관점에서 더 의미 있게 관리할 수 있게 되었고, 실제 플레이 데이터를 기반으로 난이도 스파이크와 특정 빌드 편차를 분석할 수 있는 구조를 만들었습니다.

### 버전 3. 운영/데이터 수집 중심 + 개발자 마음가짐

- A lonely green slime (1인 개발, 사용 기술스택 : JavaScript, Phaser, Django REST Framework)
A lonely green slime은 게임을 좋아하는 마음에서 시작한 Phaser 기반의 웹 액션 게임 프로젝트로, 단순히 플레이 가능한 상태를 만드는 데서 그치지 않고 Django REST API를 연동해 운영과 개선까지 고려한 형태로 개발했습니다.
개발을 진행하며 "재미로 만든 게임이라도 실제 유저의 플레이 경험은 데이터를 통해 더 나아질 수 있어야 한다"는 생각이 들었고, 플레이 감각에만 의존한 밸런스 조정에는 한계가 있다고 판단했습니다.
이를 해결하기 위해 기간별 리더보드(`7d`, `30d`, `1y`)를 분리하고, 동일 닉네임은 최고 기록만 반영하도록 집계 로직을 설계했으며, 익명 플레이로그 수집 기능을 구현해 플레이 시간, 피격 유형, 최종 점수, 분 단위 스냅샷, 장착 뱃지 정보를 저장하도록 구성했습니다.
이 과정에서 실제 유저의 플레이 흐름을 바탕으로 난이도 스파이크와 특정 빌드 편차를 분석하고 서비스 품질을 높일 수 있는 구조를 만드는 데 큰 만족을 느꼈고, 사용자 경험을 꾸준히 개선할 수 있는 제품을 만들고 싶다는 개발자로서의 방향성을 더욱 분명히 하게 되었습니다.
